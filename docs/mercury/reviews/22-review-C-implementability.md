## 2. Summary verdict

**Not yet implementable as one integrated design. The core is sound; the seams are not.** Three things hold together:

- the transition-engine and outbox core: one transaction per transition, append-only authority tables, derived review validity, fencing;
- the run adoption model;
- the authority invariants.

They also accommodate almost everything B, D and E ask for. But the four integration surfaces were designed in parallel, and they disagree on concrete contracts that an implementer would hit in the first weeks:

1. **GitHub gate mechanics.** My transitions post a bot `REQUEST_CHANGES`, which deadlocks the merge path. They never publish the required `MERCURY / claude-review` check run or E's `mercury/policy` status, so with B's ruleset no PR could ever be merged (RC-01, RC-02, RC-03).
2. **Recovery semantics.**
   - D resets worktrees without archiving, and to a different checkpoint than B and I use.
   - D caps environment retries, which contradicts the sleep constraint.
   - D's restore procedure "adopts" PRs for tasks the restored DB no longer knows, which cannot be done without fabricating authority (RC-06, RC-07, RC-08).
3. **Isolation model.** E's MUST (SEC-201: a separate agent uid) and E's snapshot review (SEC-205) break assumptions in my process and worktree design and in D's (RC-09, RC-24). Per-run vs per-task `CODEX_HOME` is a direct conflict that breaks Codex resume (RC-05).
4. **Vocabulary drift.** Three names exist for the outbox, inbox and run tables. Block/hold reason codes, run statuses and invariant IDs diverge across documents (RC-10, RC-20, RC-21, RC-22).

**Counts:**
- No **Critical** finding: none violates an authority invariant, and each has a bounded fix.
- **10 High** findings would cause a deadlock, duplicate or lost work, or an unenforced security requirement if implemented as written.
- **24 Medium** and **7 Low** (41 total).

**Positive confirmations:**
- Every **state name** used by A, B, D, E and F exists in SM. The only exceptions are `DISCOVERED` (OV §9.1, VP TC-E2E-001) and `MERGE_UNVERIFIED` (TR FR-182), both known disagreements.
- Every authority binding E requires for **plan approval** (`task_id`, `auth_id`, `pln_id`, `plan_sha256`) is enforced by both a guard and a trigger.
- The derived-validity design for PR reviews satisfies SEC-308 without mutation.
- D's re-attach model and mine agree on the key point (Codex and test runs are adopted, Claude runs are re-run). My `runwrap` + `exit.json` removes D's open assumption ASM-D-16 (no exit code after re-attach).

## 4. Positions on the known disagreements

**D1. BLOCKED-with-auto-resume (A) vs holds separate from states (C).**
*Recommendation:* holds, with three fixes this review found:
- the `noSpecDrift` guard on result-consuming transitions (RC-04);
- hold effects that can emit outbox items (RC-02);
- a canonical hold vocabulary (RC-21).

*Why:*
- A condition that clears without a human must not raise the "needs you" signal. That noise is the Slack-era failure.
- A hold keeps the exact resume point, so A's "resume to which state?" problem disappears.
- B's and E's requirements (SEC-307 suspension, check `action_required`, PR to draft) are all expressible as hold effects.

**D2. `jobs` table (A) vs a queue derived from task state (C).**
*Recommendation:* derived queue.
- A `runs` row *is* the leased job, with fencing, attempts and binding columns. `nextAction(state)` is a pure function.
- A `jobs` table would be a second source of truth for "what should happen next", and it can disagree with `tasks.state` after a crash.
- The non-process actions A's jobs cover (merge verification, decision-point evaluation, outbox delivery) are covered by `MergeVerifier`, `evaluateDecisionPoint` and `outbox` respectively.
- A should rename `claimDueJobs` → `claimNextActions` in OV §6.

**D3. HMAC optional (A, C) vs required (E); no anchoring table.**
*Recommendation:* **required, with an honest threat statement.**
- Put `record_mac NOT NULL` on all three authority tables in migration 0001, verify it in the guards, and add `audit_anchors` and `audit_epochs` (RC-14, RC-15).
- *Why:* the cost is tiny, because the Keychain read already exists. Adding the columns later is a contract-class migration (RC-29).
- The value is real only against writers that cannot read the Keychain item: a sandboxed or agent-uid process. Without SEC-201, the documents must state that the MAC defends against bugs and partial compromises, not against the same uid. The anchor is the meaningful same-uid defence.

**D4. Filesystem layout.**
*Recommendation:*
- State (DB, artifacts, config, logs) under `~/Library/Application Support/Mercury` (D).
- **Work root** configurable as `paths.work_root`, default `~/Library/Mercury` (D) while agents share the operator uid.
- **Mandatory** `/Users/Shared/Mercury/work` (0750 `coordinator:mercury-agents`, per E §8.1) once SEC-201 is adopted. That is the only option an agent uid can traverse.
- Drop `~/MercuryWork` (mine) and B's `…/Application Support/…/checkouts`: the space in the path breaks build scripts, and snapshots replace checkouts (RC-24).

*Why:* only D's split satisfies both "no spaces" and "no TCC". Only E's location works with the separate uid.

**D5. Separate macOS agent user (E SEC-201 MUST) vs same-user process groups (C, D).**
*Recommendation:* adopt SEC-201 as the target and **design for it now** behind an `AgentLauncher` port (RC-09). Same-uid process groups remain the interim implementation, with E's deny-read profiles and the canary test, and R-03 is recorded as accepted until Phase 0 verifies the broker.
*Why:*
- It is the only OS-enforced control against credential theft by an injected agent, and E's single-control-failure analysis rests on it.
- The process model changes it requires (cross-uid signalling, umask/setgid, `safe.directory`, work-root location) are bounded and can be listed. Retrofitting them after M5 would touch the supervisor, worktree manager and commit pipeline.

**D6. Merge governance: G-1/G-2 (A) vs G-ORG/G-SPLIT/G-DETECT (E) vs B's detect-after.**
*Recommendation:* G-ORG as the target before unattended use. G-DETECT with written risk acceptance for the sandbox and pilot. G-SPLIT only if ASM-E-01/02/07 pass in Phase 0.
*Data-model impact (my focus):*
- `repos.governance_mode` and `merge_verifications.control_kind ∈ {preventive, detective}` must exist, so FR-182 and CON-014 reporting can state per repo which kind applies.
- G-SPLIT needs a second credential path (deploy key) for `git.push` outbox items: `outbox.credential_profile`.

These are additive. The operator decides the mode.

**D7. `revision_request` as a separate Claude decision (B) vs verbatim forwarding (C).**
*Recommendation:* keep verbatim forwarding for revisions whose source is already a validated Claude verdict (plan or PR review). Use a Claude `revision_request` run for CI, tests, human comments, conflicts and Codex-reported `blocked` (RC-13).
*Why:*
- The verbatim text *is* Claude's decision, bound by hash.
- A second run adds cost and latency and a second injection surface (it re-reads the same untrusted content), and it decides nothing new.
- Concession to B: when **both** reviews request changes and their `required_change` texts conflict (same path, incompatible instructions), the coordinator must not merge them heuristically. It dispatches a `revision_request` run to consolidate. Add this as a V4 rule.

**D8. Linear status ownership.**
*Recommendation:* B's default `integration_owns_pr_states`. MERCURY writes only → `In Progress` and the `mercury:needs-human` label, and its projection is mode-dependent (RC-11). On A's "who closes": in the default mode the integration closes, and MERCURY's merge verification is the only "verified" signal, published as a comment.
*Why:* two writers of one Linear field flap (FR-183), and the branch name already contains the issue ID. `mercury_owns_all` stays available if the operator wants a verified `Done` (OD-06).

**D9. Requirement-ID schemes.** F's scheme (FR/NFR/CON/OPS, SEC sub-ranges for E) is canonical, because the brief names F as the owner. Migrations:
- A's NFR-xxx-nn → F IDs;
- D's REL-01…15 → NFR-02x;
- SM invariants → `SMI-nn`, VP properties → `PROP-nn` (RC-20);
- F's `ADR-P01…P15` → A's `ADR-001…012`, plus new ADRs for gaps such as filesystem layout or a separate uid. A publishes the mapping in Phase 4.

**D10. Re-attach vs re-run after a crash.** There is no real disagreement. C and D both adopt Codex and `verify`/`deps_install` runs and re-run Claude runs. Remaining deltas:
- Use `runwrap` + `exit.json`, which removes D's unknown-exit-code assumption.
- Always archive before any worktree reset, and never resume a thread over a reset tree (RC-06).
- D's "rebooted → mark interrupted without probing" shortcut is fine (pids are invalid after a reboot) and consistent with my identity check.

**D11. `DISCOVERED` removed as a task state (C) vs the brief.**
*Recommendation:* keep it at the **issue level** (`linear_issues.mercury_status = 'discovered'`), as the brief allows renames with justification.
*Why:* a task row means "authority is being sought or exists". Making every backlog issue a task destroys the one-active-task-per-issue index's meaning.
Follow-up: VP TC-E2E-001 should read "issue discovered → task COMPLETED", and OV §9.1's projection row should be split.

**D12. `MERGE_UNVERIFIED` / integrity alert.**
*Recommendation:* `BLOCKED(merge_verification_failed)` plus a repo-scoped `integrity_alert` hold, with the waiver inserted as a new row (RC-17). Not a new state, and not `MERGED` + flag.
*Why:*
- It needs a human, so it belongs in `BLOCKED`, with its reminders, resume table and notification dedup.
- Leaving it in `MERGED` would make `MERGED` mean both "verification pending" and "verification failed", and the dispatcher would keep re-verifying.
- A new state would duplicate `BLOCKED` semantics.
- The repo hold delivers B's "pause the repo" behaviour.
