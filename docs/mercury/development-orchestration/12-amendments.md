# 12 — Proposed Roadmap Amendments, ADR Amendments and Operator Decisions

None of these is in effect. Each needs operator approval. **The TDD's design is not changed** by this package. The amendments add a development-process layer and roadmap sequencing advice. Revised for devorch v2 after reviews R1–R4 (dispositions: `reviews/R0-dispositions.md`, upcoming).

## 1. Proposed ADR

**ADR-021 (Proposed): Temporary development orchestration for building MERCURY.** Draft: `architecture/decisions/proposed/ADR-021-development-orchestration.md`.

- Records the decision to build MERCURY with a Claude Code main-session orchestrator and 12 project subagents, with a hash-chained git ledger on `devorch/state` written only through `devorch.py` by the orchestrator or the operator.
- Records the separation rules S1–S4 (`01-…` §1) and that the development system holds no production authority.
- Records that the settings deny rules and the specialist guard hook are tripwires; the real controls are the `main` ruleset (DOD-02) and the development bot identity (DOD-03).
- **Interaction with existing ADRs:** none superseded.
  - ADR-003 is unaffected; the development hub-and-spoke model mirrors it.
  - ADR-008 is unaffected: development identities are separate (DOD-03, S2).
  - ADR-014 / roadmap P0d ("govern MERCURY's own repository like a target"): the operator-applied ruleset and CODEOWNERS protect `main` from the bootstrap on (RA-D9). MERCURY's own required checks (`claude-review`, `policy`) cannot exist until MERCURY runs, so RA-D2 proposes a recorded, time-boxed exception until self-hosting Stage D. RISK-45's trigger (human-credential automation on the MERCURY repo) is handled by DOD-03 (a), mandatory for code PRs.
- On acceptance, the ADR index (RD-10: "ADR-001…020 canonical") is amended and "Proposed" is added to its status vocabulary (R1 L-04).
