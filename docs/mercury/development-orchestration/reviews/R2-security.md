# R2 — Independent security review of the development orchestration package

Reviewer: `mdev-security-engineer` role (independent, read-only; no repository edits other than this file). Date: 2026-10-15. Branch `claude/dev-orchestration`, head `73ad09e`.

## 1. Scope and method

In scope (as requested by the Phase 14 review brief):

1. Whether any agent, including the Principal Orchestrator, can obtain human GitHub approval or merge authority (MCP tools, `git push`, `gh`, REST via `curl`, the operator-identity problem DOD-03, absence of a `main` ruleset DOD-02).
2. The security and authorization matrix (`08-quality-gates-and-security.md` §4) against the actual configuration (`.claude/settings.json`, `.claude/agents/*.md`, `tools/devorch/gen_agents.py`).
3. `.claude/settings.json` deny-rule syntax, gaps, and false positives against legitimate work.
4. Whether the development system can weaken the production security model (SEC-204, SEC-209, SEC-310, CON-008, credential separation, self-hosting stages in `11-…`).
5. Prompt-injection handling (`08-…` §6, agent rule 7).
6. Privileged host actions.
7. Supply chain (dependencies, CI workflows).

Method: read the package (README, 00–13, agents, settings, CLAUDE.md, `tools/devorch/*`), the relevant parts of `docs/mercury/TDD.md` and `docs/mercury/security/threat-model.md` (SEC-204, SEC-209, SEC-310, SEC-702, §merge-path table), and inspected the live environment read-only (git remote/config keys only, never values; tool inventory of this session). No GitHub/Linear writes and no push attempts were made; exploit paths below are therefore reasoned from configuration and documented Claude Code behaviour, and marked UNVERIFIED where a live write would be needed to prove them.

## 2. Verdict

**Not ready** for any implementation work (code PRs). **Ready with conditions** only for the current docs-only PR, which the operator reviews and merges by hand.

The package is honest that settings/`disallowedTools` are "not a security boundary" and that the real boundary is the `main` ruleset plus a separate development identity (DOD-02/03). That analysis is correct, but it means that **today there is no boundary at all**: no ruleset exists, every agent process runs as the same OS user with the operator's GitHub authorization, and several unblocked paths let any agent with Bash, or the main session without the `--agent` allowlist, write to `main` directly. DOD-02 and DOD-03 (option a) must be hard preconditions of Stage A, enforced mechanically, not just recommended "before the first code PR".
